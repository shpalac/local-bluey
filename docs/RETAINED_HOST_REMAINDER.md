## Settings and privacy: distinct source owners

[SettingsStore](../lib/services/settings_store.dart) loads current endpoint/backend/model from SharedPreferences and the API key from secure storage. Missing fields take defaults; secure-read failure is caught, returns no key and records a warning, rather than necessarily failing host reload. Preference acquisition/type errors can propagate. `buildBrain` constructs a provider and persona locally; it does not make a connection or verify the model. Save writes secure storage first, then individual preference fields; this is not a versioned atomic settings/privacy transaction. `clearAll` removes settings and the key; it does not reset an already retained Brain or cancel transport. Removal return values are not all checked. These are inspected owner semantics, not a new deletion task.

[PrivacyGuard/LocalOnlyPreferences](../lib/services/privacy_guard.dart) is separate. Ordered read/write/clear uses revisions, a clear epoch and post-write reconciliation. Failed current read returns typed `PrivacyStorageException`; a recovery read may publish an actual verified bool, otherwise `value` is null. Unknown is not fabricated OFF. Successful missing-key reads/default after clear are false. Older queued choices cannot undo the completed clear; a fresh later choice can persist. A verified last value is not permission for a caller to skip its required fresh read. Production is not the `debugLocalOnlyOverride` fixture.

`refusalForUrl` reads this preference and classifies loopback-only HTTP(S); remote/LAN/malformed URLs are refused when local-only is true. False allows the endpoint under this existing guard; uncertainty throws. The function proves its own result, not that every provider calls it. No DNS/native/network readiness follows from classification.

[Settings UI](../lib/ui/settings_screen.dart) persists the privacy toggle before reporting success, reconciles retained/unknown state and contains safe errors. Its connection test checks current privacy before egress recording, then rechecks after that await before constructing/calling the form's provider; uncertainty has a safe failure branch. That explicit test uses the current form, not BrainHost, and does not protect unrelated consumers. STT [upload](../lib/services/stt.dart) checks its separately loaded endpoint and snapshots the local-only decision for that upload/redirect scope. TTS [synthesis](../lib/services/speech.dart) checks its resolved speech endpoint. Neither check is a blanket authorization or guard for a later retained brain call.

## Coherent retention and caller containment

[BrainHostState](../lib/services/brain_host.dart) takes latest reload generation through settings load and privacy refusal, builds only if allowed, stages brain/refusedReason/remoteActive before notifications and fences reentrant publication. Successful refusal publishes null brain/reason/remote false. Current load/refusal/build exceptions retain the prior coherent snapshot, deliver pending coherent notifications and rethrow. Stale exceptions/results are discarded. First failure can leave the initial null/null/false; failure after a refusal keeps that refusal, and failure after allowed remote construction can keep that remote Brain. A retained remoteActive value describes the last published URL, not a fresh verification or an HTTP observation.

[HostReloadController](../lib/services/host_reload_controller.dart) installs pending completion before notifications; repeated explicit retry joins entered work. Fresh reload takes latest caller ownership. It catches dependency failures, publishes generic current failed/loading state, rejects disposed entry and defers notifier disposal out of notification. It does not null/reset the retained provider, cancel an entered request or disable admission. [HostReloadNotice](../lib/ui/host_reload_notice.dart) states "Previous state is retained" and offers explicit Retry; it is not a fail-closed network indicator.

All five [MacHome](../lib/main.dart) paths use that owner: startup, saved normal Settings return, saved onboarding Settings return, and both delete-all callbacks. Delete-all callbacks also return the UI to onboarding. [Registry deleteAll](../lib/services/data_registry.dart) clears stores sequentially, reports failed stores before final preference/secure clear, and [Settings callback](../lib/ui/settings_screen.dart) reaches the host only after its deletion notification. Partial deletion does not prove all configuration is gone. Neither successful storage removal nor a subsequent failed host reload automatically erases the retained Brain/provider credentials/history. No additional lifetime or deletion policy is selected here.

## Every retained-host consumer

A full current `lib` search for BrainHost/buildBrain/buildProvider and provider/brain calls found these distinct consumers, not just the reload helper:

- **Request entry:** face, key and phone audio converge on [RequestRunner](../lib/services/request_runner.dart). It admits one active File plus two waiting slots by default, snapshots safety generation, rejects overflow and discards stopped queued work. Its whole-job deadline starts at run entry, not queue admission. Fresh settings/STT settings load and transcription happen before `brainProvider()` lazily reads the current retained host. A failed settings load ends the run; a null brain gives setup guidance. A successful fresh settings load does not rebuild or validate the retained Brain. Those settings later configure TTS; the selected Brain's immutable endpoint/key/model may still be older. No HostReloadController.failed/refusedReason or fresh brain-endpoint privacy check is consulted here.
- **Entered request/tool work:** the chosen Brain is held in the run after selection, even if a newer reload replaces the host. [Brain](../lib/llm/brain.dart) askStreaming invokes provider.chatStream; toolResult invokes chatWithTools. Safety authorizes actual tools before execution, including reporting denials back through toolResult. Safety is not an endpoint privacy guard. Brain.ask also uses chatWithTools and may consolidate overflow through provider.chat, but the current request caller uses askStreaming rather than ask. Reset fences late replies/tokens/memory; it does not physically cancel an entered transport or undo actions. Request stage timeout/generation checks suppress later publication/effects, not already-entered network work or provider retry.
- **Watch inference:** [main](../lib/main.dart) resolves `BrainHost.brain.value?.provider` into [WatchVision](../lib/services/watch_vision.dart). It uses stateless immutable screen input, no Brain history/memory/tool execution. It selects the provider before an awaited snapshot and keeps that object for the later inference. A subsequent host replacement alone does not swap that entered operation's provider. Null provider refuses capture/inference. No retained-endpoint URL classification occurs in WatchVision.
- **Stop/reset:** the main safety-kill listener resets the currently published Brain and key intent. It does not necessarily reset a different Brain already captured by an older request after host replacement. Request safety generation still fences that request's result. Watch Stop remains its separate session-generation control.
- **Display:** main listens to refusedReason and reads remoteActive for the refusal/cloud banner. These are coherent retained source-derived indicators, not proof of current preference/settings verification, admission blockage or transmission. Host retry notice is independent. No other current lib consumer of these snapshot notifiers was found.

## Actual provider guards, and what they do not guard

The actual [Ollama](../lib/llm/ollama_provider.dart) and [OpenAI-compatible](../lib/llm/openai_compatible_provider.dart) methods were read, along with [LlmProvider](../lib/llm/llm_provider.dart) defaults and [Brain](../lib/llm/brain.dart). They do **not** call PrivacyGuard in chat, chatWithTools or chatStream. They construct their stored URL/payload and invoke HTTP post/send. Nonstream chat/tool calls use [typed bounded retry](../lib/llm/retry.dart); stream methods do not use that retry wrapper. Egress recording after nonstream post is history, not an admission guard; stream methods have no corresponding record call here. The guard at host construction is real, but is not repeated by these methods.

Thus retention alone is not proof of a privacy bypass. A conditional source path exists: an older allowed remote Brain is retained after current reload failure; a later request successfully completes its fresh settings/STT stages and selects that object, or an allowed watch inference resolves it; the transport has no further brain-endpoint check. Whether those preconditions occur together, which endpoint is actually contacted, and whether any bytes leave were not tested in this audit. Conversely caller error containment cannot prove fail-closed transmission. Do not infer that read uncertainty permits operation; a boundary that actually performs a fresh privacy read throws/refuses as described above.

## Watch gates remain real, but separate

[WatchScreen](../lib/ui/watch_screen.dart) prepares current scope and shows per-session consent, catches policy/start errors and does not start on declined consent. [ScreenWatch](../lib/services/screen_watch.dart) checks local-only, allowlist/denylist and scope again before start. Each operation checks active generation, current policy and expiry; uncertainty stops the session and returns refusal. [Pipeline](../lib/services/watch_pipeline.dart) gates frontmost/window/lock before deeper work. WatchVision performs a second gate after capture; stop/current-generation checks fence late capture/inference results. [Driver](../lib/services/watch_driver.dart) contains current tick errors, stops ticking and clears its buffers, rather than leaking a timer future; that is not necessarily the same state as ending ScreenWatch's session.

Those checks bind the current local-only bool and app/session, not the selected provider's stored URL. An ON preference alone does not classify a retained remote endpoint. A read failure in a gate suppresses new inference, but a later gate does not retroactively abort HTTP already entered. Provider/host identity can change while capture is held without changing the watch session generation. These are source-derived composition questions, not a new image-sanitation/consent policy or proof of real capture. [#351](https://github.com/shpalac/local-bluey/issues/351) remains held and unchanged.
