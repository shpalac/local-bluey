## Identity, signature and verification contract

A later selected manifest should bind schema, source commit/tag/build number, exact filename/byte size/SHA256, platform/arch/minOS, toolchain/runner/dependency provenance, bundle/application id, expected signer/certificate or policy reference, required notices, attestation subject and verifier-policy revision. Pin exact selected inputs; never use 'latest', runner label, archive name or displayed app branding as identity. Preserve source and artifact digest across extraction/install; classify unsupported platform versus missing/bad evidence explicitly.

GitHub [verification CLI](https://cli.github.com/manual/gh%5Fattestation%5Fverify) validates artifact/actor identity and predicate, not functionality, safety or distribution signing. Minimum repo constraint is not exact workflow/source identity. Later policy should constrain expected repo, signer workflow/ref/digest, source commit/ref and predicate, check subject bytes and verified certificate/timestamps, and treat workflow-controlled predicate fields as claims. Reusable workflow signer rules matter if one is adopted. No attestation verifier or trusted-builder policy is installed or chosen here.

[Offline verification](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline) requires previously acquired artifact, bundle, trusted roots and verifier. Online acquisition is a distinct authorized step. Frozen roots may miss later rotations/revocations; record snapshot/freshness/policy and fail missing roots/bundle/identity, never silently fetch or pass unknown verification. Checksums from the same untrusted archive/list do not authenticate a publisher. Existing pub-only SBOM and #646 preparation do not resolve full native/license coverage.

## Proposed inert runner and acceptance

First a fake-only typed runner can consume tiny local manifest/archive fixtures and injected verifier/process/device hosts. Stages: validateManifest, verifyBytes/provenance/signature, inspectPackage, selectIsolatedTarget, install, launch, observe, stopAndClean. Immutable run id/generation, exact target/artifact identity and bounded receipts pass forward; unsupported/missing/denied/hashMismatch/signatureMismatch/installFailed/launchFailed/observationFailed/timeout/cancelled/cleanupFailed are explicit. A later UI/CLI must show preparation versus executed versus accepted, never a green boolean hiding an unrun stage.

Bound file count/size/path depth/decompression output; reject absolute/traversal/escape symlink paths, duplicate unexpected binaries, executable drift, stale receipt and policy mismatch before extraction/install. Pin schema/parser/verifier policy; stable sorted keys/digests make decision reproducible, diagnostic timestamps separate. No shell command constructed from archive metadata; execute bounded allowlisted argv through an injected host. Fake fixture gate stays offline/secret-free and produces no permission prompt or real launch.

Each awaited stage needs selected timeout/cancellation plus cleanup of only its own child/tempdir/test target. Signal delivery is not confirmed child exit. Fence late outputs after stop/restart, await cleanup receipt before marking complete; retain incomplete state when termination/cleanup unverified. Don't reboot/shutdown unrelated available simulators, kill by shared bundle-name alone or uninstall personal app/data. Persist only sanitized manifest/phase/status/error code/evidence hash, no credential/private paths/user screenshot/audio. Offline or unavailable verifier/device is blocked/unsupported, not skipped-as-pass.

Later disposable install/launch evidence should include fresh install and supported update, corrupt package/missing resource/library/wrong arch, wrong signer/version/bundle/attestation, denied install/permission, startup crash/timeout, wrong target/race/late output and restart. Observe exact launched child plus selected visible initial state and no unintended network/capture/effect before opt-in; survival alone is not app acceptance. Use fabricated UI/data. Screenshot checks require actual pixel inspection under a separate sanitized evidence policy, not automatic raw screen upload.

Existing VALIDATION checklist still needs owner physical Mac/iPhone run: named device/OS/build, grants, pairing/reconnect, voice and confirmed action/Stop, local-only, secure settings/delete. That is outside a hosted release smoke gate. Current root-key/fake permission/link fixtures cover control flow/configuration only. Never turn missing physical evidence into an assertion 'verified on all platforms'.

## Fixture sequence, reporting and rollback

Next independent fake-only slice, if manager selects: typed manifest/results/parser first, injected verification evidence next, then injected install/launch/cleanup lifecycle. Negative fixtures: absent signature/notice/roots, misleading latest identity, mismatch digest/subject/signer/source, incomplete platform coverage, path traversal/zipbomb/symlink escape, wrong target, unsupportedOS/arch, installer failure, launched wrong process, crash before observation, cancelled joined wait, timed-out child still alive, partial cleanup, stale completed receipt and changed-policy invalidation. These tests would prove decisions/order, not actual signing/install/native acceptance. No new fixtures implemented here.

A later release response blocks publication on incomplete/denied required stages, rather than silently removing a platform or treating skipped optional native tests as proof. Keep statuses/source/target/evidence explicit and link a sanitized failure, not raw device logs or private signing material. Existing build log/simulator screenshot uploads have no general scrub step; GitHub masking is not a universal data guarantee. Source-visible settings 404/403/null caveats in #592 audit are not proof disabled; no settings changes requested.

Rollback selects a previously verified exact artifact with compatible signer/data/protocol/schema, tests supported restoration and keeps explicit user data policy. Android version/signing and iOS distribution constraints mean downgrade may be disallowed; do not bypass platform trust checks, overwrite keys or delete data to force it. A gate rollback is a separately reviewed config change, not this plan. Quarantine a failing candidate, preserve bounded diagnostics, manager/owner chooses repair/release withdrawal; no destructive cleanup or release action assumed.
